# 분석 API 안정화 및 비동기 작업 전환 제안서

## 1. 목적과 배경

현재 서버는 시작 단계에서 최신 ETF 스냅샷 확인과 최근 12개월 가격 이력 백필을 동기 실행한다. 이력 DB가 비어 있으면 평일 약 260일에 대해 KRX API를 날짜별로 순차 호출한다. 이 동안 FastAPI가 준비 상태가 되지 않아 브라우저에서 `ERR_CONNECTION_TIMED_OUT`가 발생할 수 있다.

이 문서는 외부 데이터 API의 지연·실패·호출 제한, 빈 로컬 캐시, 개발 서버 자동 재시작, 배포 환경 재시작 상황에서도 서비스가 요청을 받을 수 있도록 구조를 전환하는 제안이다. 분석 결과는 계속 정보 제공 목적이며, 외부 데이터 실패 시 검증된 캐시 결과와 한계를 함께 표시한다.

## 2. 현재 문제와 원인

| 문제                                | 현재 원인                                                | 사용자 영향                                        |
| ----------------------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| 서버 접속 시간 초과                 | `lifespan`에서 12개월 백필을 완료할 때까지 기동이 지연됨 | 화면의 API 요청이 연결 대기 후 실패                |
| KRX 요청 과다                       | 누락된 영업일마다 개별 POST 요청을 순차 수행             | 시작 시 수백 건 호출, 호출 한도·네트워크 부담 증가 |
| 재시작 시 작업 반복                 | 이력 데이터는 전체 호출 완료 뒤 저장됨                   | 중단·자동 재시작 시 같은 범위를 다시 요청 가능     |
| 긴 분석의 HTTP 의존                 | 뉴스·AI 단계까지 하나의 요청에서 처리                    | 프록시·브라우저 타임아웃, 진행 상황 미표시         |
| 외부 장애가 체감상 서버 장애로 보임 | 부분 실패가 화면에 명확히 구분되지 않음                  | 사용자가 네트워크 끊김으로 오인                    |

## 3. 목표 상태와 비목표

### 목표

- 서버는 외부 API 상태와 무관하게 빠르게 기동하고 `/health`에 응답한다.
- 분석·백필 같은 장기 작업은 HTTP 요청 처리와 분리한다.
- 사용자는 작업 진행, 부분 실패, 최종 결과를 새로고침 없이 확인할 수 있다.
- 작업 중단 후에도 이미 저장한 날짜부터 이어서 처리한다.
- 외부 API 호출량과 동시성을 설정값으로 제한한다.

### 비목표

- SSE를 주문·실시간 시세 스트리밍 용도로 사용하지 않는다.
- 사용자 계정·장기 분석 이력 기능을 이번 변경 범위에 추가하지 않는다.
- SSE만으로 서버 시작 지연을 해결하려 하지 않는다. 서버가 준비된 뒤의 작업 상태 전달에만 사용한다.

## 4. 권장 아키텍처

```text
Frontend
  ├─ POST /api/analyses              -> 202 + job_id (즉시 반환)
  ├─ GET  /api/analysis-jobs/{id}    -> 현재 상태·최종 결과 재조회
  └─ GET  /api/analysis-jobs/{id}/events -> SSE 진행 이벤트 수신

FastAPI API
  ├─ 즉시 기동: DB 초기화·헬스 체크만 수행
  ├─ Job 관리: 입력 검증, 작업 생성, 상태 조회, SSE 연결
  └─ Worker: ETF 갱신 → 정량 분석 → 뉴스 → 감성 → 결과 저장

SQLite
  ├─ ETF 일별 캐시: 날짜별 즉시 저장
  └─ 분석 작업: 상태·단계·진행률·안전한 오류·결과 요약
```

초기 구현은 별도 메시지 브로커 없이 애플리케이션 내부 worker로 시작할 수 있다. 다만 다중 프로세스/다중 인스턴스 배포, 높은 동시 요청 또는 재시작 뒤 작업 보장이 필요해지면 Redis 기반 큐와 독립 worker로 분리한다.

## 5. 서버 기동과 캐시 정책

| 항목               | 제안 정책                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| FastAPI `lifespan` | SQLite 스키마 준비와 가벼운 상태 확인만 수행. KRX 수집·12개월 백필 금지                                                      |
| 최신 ETF 데이터    | 분석 작업 시작 시 캐시가 유효하면 재사용, 없거나 오래됐으면 해당 작업 안에서 최신 1일만 갱신                                 |
| 12개월 이력        | 별도 `history_backfill` 작업으로 실행. 분석 작업은 이미 확보된 이력으로 계산하고 부족하면 지표별 `insufficient_history` 표시 |
| 저장 단위          | KRX 날짜 하나 또는 작은 배치마다 트랜잭션으로 저장. 재시작 뒤 DB에 없는 날짜만 재요청                                        |
| 자동 실행          | 개발 환경은 명시적 실행만 허용. 운영 환경은 하루 1회 스케줄 또는 관리자 트리거로 제한                                        |
| 호출 제한          | KRX 요청 간 최소 간격, 최대 동시성 1, 총 작업 시간·재시도 횟수·지수 백오프를 환경변수로 관리                                 |

이 정책으로 DB가 비어 있어도 화면과 API는 즉시 사용 가능하며, 이력이 부족한 결과를 정직하게 반환한다.

## 6. 공개 API 초안

### 6.1 분석 시작

`POST /api/analyses`

- 요청 본문은 기존 `AnalysisRequest`를 유지한다.
- 입력 검증 실패는 기존처럼 `422`를 반환한다.
- 정상 접수는 `202 Accepted`와 아래 내용을 반환한다.

```json
{
  "job_id": "uuid",
  "status": "queued",
  "status_url": "/api/analysis-jobs/uuid",
  "events_url": "/api/analysis-jobs/uuid/events"
}
```

동일한 `client_request_id`가 진행 중이면 새 외부 호출을 만들지 않고 기존 작업 정보를 반환하는 정책을 권장한다.

### 6.2 작업 상태 조회

`GET /api/analysis-jobs/{job_id}`

응답의 상태는 `queued`, `running`, `completed`, `partial`, `failed`, `cancelled`, `expired` 중 하나다. `completed`와 `partial`에는 현재 `AnalysisResponse`와 호환되는 결과를 포함한다. SSE 재연결 실패·페이지 새로고침·접근성 대체 수단으로 사용한다.

### 6.3 SSE 이벤트

`GET /api/analysis-jobs/{job_id}/events`

응답 헤더는 `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`를 사용한다. 서버는 15초 이하 간격의 keep-alive를 보내 프록시의 유휴 연결 종료를 줄인다.

| 이벤트     | 필수 데이터                              | 용도                                 |
| ---------- | ---------------------------------------- | ------------------------------------ |
| `status`   | `job_id`, `status`, `updated_at`         | 대기·실행·완료 상태 전환             |
| `progress` | `stage`, `completed`, `total`, `message` | 예: `history_backfill`, 34/260일     |
| `warning`  | `code`, `message`, `retryable`           | 외부 공급자 부분 실패 안내           |
| `result`   | `status`, `result`                       | 최종 `completed` 또는 `partial` 결과 |
| `error`    | 안전한 오류 코드·메시지                  | 복구 불가능한 실패                   |

SSE는 서버→브라우저 단방향 전달만 필요할 때 적합하다. 취소 기능은 별도 `POST /api/analysis-jobs/{job_id}/cancel`로 제공한다.

## 7. 작업 상태·복구 모델

작업 테이블에는 `job_id`, 입력 조건, 상태, 현재 단계, 생성·갱신 시각, 진행 수치, 결과 JSON, 안전한 오류 목록만 저장한다. API 키, 원문 예외, 뉴스 원문 전체는 저장하지 않는다.

| 단계               | 성공 조건                       | 부분 실패 처리                      |
| ------------------ | ------------------------------- | ----------------------------------- |
| `etf_snapshot`     | 최신 스냅샷 또는 유효 캐시 확보 | 캐시도 없으면 작업 실패             |
| `history_backfill` | 필요한 날짜가 저장됨            | 부족 이력으로 정량지표 일부 보류    |
| `quantitative`     | 계산 가능 후보·상태 산출        | 후보별 산출 불가 사유 유지          |
| `news`             | 검증된 뉴스 수집                | 뉴스 없음·공급자 실패를 경고로 유지 |
| `sentiment`        | 근거 충분 ETF만 분석            | AI 실패 ETF만 제외                  |
| `portfolio`        | 정책을 통과한 결과 조립         | 근거 부족이면 포트폴리오 보류       |

worker 시작 시 `queued`와 비정상 종료된 `running` 작업을 검사한다. 오래된 작업은 한 번 재시도하거나 `failed`로 확정하고, 중복으로 외부 요청하지 않도록 실행 잠금을 둔다.

## 8. 프런트엔드 동작

1. 분석 시작 응답에서 `job_id`를 받는다.
2. 즉시 `EventSource(events_url)`를 열고 단계별 진행률과 사용자용 메시지를 표시한다.
3. `result` 이벤트 수신 시 기존 결과 렌더러에 결과를 전달하고 SSE를 닫는다.
4. SSE 오류 또는 20~30초 동안 이벤트가 없으면 상태 조회 API를 한 번 호출하고, 필요 시 지수 백오프로 SSE를 재연결한다.
5. 브라우저가 SSE를 지원하지 않거나 연결이 반복 실패하면 상태 조회 API를 저빈도 폴백으로 사용한다.

따라서 HTTP 폴링을 주 통신 방식으로 쓰지 않되, SSE가 끊겨도 결과 확인이 불가능해지지 않는다.

## 9. 환경 설정 제안

실제 비밀값 없이 `.env.example`에 아래 설정을 문서화한다.

```env
ANALYSIS_WORKER_MODE=in_process
ANALYSIS_JOB_MAX_SECONDS=180
ANALYSIS_SSE_HEARTBEAT_SECONDS=15
KRX_REQUEST_TIMEOUT_SECONDS=15
KRX_MIN_REQUEST_INTERVAL_SECONDS=0.5
KRX_BACKFILL_BATCH_DAYS=5
KRX_BACKFILL_ON_STARTUP=false
KRX_BACKFILL_MAX_RETRIES=2
```

배포 환경에서는 프런트의 실제 Origin을 `ALLOWED_ORIGINS`에 추가하고, 역프록시가 SSE 응답을 버퍼링하지 않도록 설정한다. 여러 인스턴스에서는 in-process 작업·메모리 이벤트 브로커를 사용하지 않고 공유 큐와 공유 상태 저장소를 사용한다.

## 10. 단계별 전환 계획

| 단계 | 변경 내용                                              | 완료 기준                                          |
| ---- | ------------------------------------------------------ | -------------------------------------------------- |
| 1    | `lifespan`에서 KRX 수집·백필 제거, 최신 캐시 우선 분석 | DB가 비어도 `/health`와 API 서버가 즉시 준비됨     |
| 2    | 날짜별 저장·중단 후 재개 가능한 백필 서비스 구현       | 재시작 뒤 이미 저장된 날짜를 재요청하지 않음       |
| 3    | 작업 상태 저장소와 `202 + job_id` API 추가             | 긴 작업이 HTTP 요청을 점유하지 않음                |
| 4    | SSE 이벤트 및 프런트 진행 UI 추가                      | 진행·부분 실패·완료가 새로고침 없이 표시됨         |
| 5    | 취소, 작업 만료, 중복 요청 방지, 관측성 추가           | 장애·재시작·중복 클릭 시 예측 가능한 상태 유지     |
| 6    | 필요 시 독립 worker/큐로 분리                          | 다중 인스턴스 환경에서도 작업이 중복·유실되지 않음 |

## 11. 검증 계획

| 시나리오          | 확인 방법                           | 기대 결과                                              |
| ----------------- | ----------------------------------- | ------------------------------------------------------ |
| 빈 DB로 서버 시작 | KRX 응답을 느리게 모의              | `/health`가 즉시 200, 기동 중 수백 건 KRX 호출 없음    |
| 빈 DB 분석 요청   | 분석 작업 시작                      | `202` 즉시 반환, SSE에 스냅샷·백필 진행 이벤트 표시    |
| worker 재시작     | 일부 날짜 저장 뒤 중단·재시작       | 저장된 날짜는 건너뛰고 누락 날짜만 재개                |
| KRX 타임아웃      | collector가 timeout 예외 발생       | 작업은 안전한 오류·부분 결과를 남기고 서버는 계속 응답 |
| SSE 단절          | 브라우저 연결을 강제로 끊음         | 재연결 또는 상태 조회로 최종 결과 복구                 |
| 뉴스·AI 실패      | 각 어댑터 실패 주입                 | 정량 결과는 유지하고 단계별 경고 표시                  |
| 동시 요청         | 같은 `client_request_id` 두 번 전송 | 작업이 중복 생성되지 않음                              |
| 프록시 배포       | 실제 Origin·SSE 버퍼링 설정 검증    | CORS 오류·이벤트 버퍼링 없이 수신                      |

## 12. 결정이 필요한 사항

- MVP에서 작업 상태를 SQLite에 얼마나 오래 보관할지(예: 24시간 후 자동 삭제)
- 이력 백필을 사용자 분석 요청과 함께 실행할지, 완전히 별도 관리 작업으로 제한할지
- 단일 인스턴스에서 in-process worker를 허용할지, 초기부터 Redis/독립 worker를 도입할지
- 작업 시간 제한, KRX 호출 간격, 재시도 횟수의 운영값
- 분석 결과의 기존 `200` 동기 계약을 유지할 호환 기간 및 프런트 전환 일정

## 13. 권장 결정

현재 MVP에는 다음 조합을 권장한다.

1. 서버 시작 백필을 즉시 제거한다.
2. 최신 스냅샷은 캐시 우선으로 사용하고, 이력은 별도·재개 가능한 작업으로 전환한다.
3. `POST /api/analyses`는 `202 + job_id`로 바꾸고 SSE를 기본 진행 채널로 사용한다.
4. SSE 실패 대비 상태 조회 API를 유지한다.
5. 첫 배포는 SQLite 작업 저장소와 단일 worker로 시작하되, 다중 인스턴스 전에는 Redis 기반 큐로 전환한다.

이 순서는 현재의 서버 기동 타임아웃을 먼저 제거하면서도, 장기 분석에 필요한 사용자 진행 안내와 장애 복구 기반을 마련한다.
